# Review of the five rewrites against Blender's source and the removed code (21 November 2026)

Reviewer: a separate reviewer, who wrote neither the descriptions nor the replacements, 21 November 2026.
This is the code review named in the project's decision:
"Preserve the existing numerical reference tests, document the independent mathematical basis of each
replacement, and review the resulting implementations for copied structure or expression." The reviewer is
not a lawyer. Everything below is an informed technical opinion about similarity, not a legal finding.

## 1. Method

For each piece three texts were read side by side: Blender's source, the removed implementation, and the
new implementation. The description document, the implementer's notes and the implementer's Provenance
paragraph were then checked against what the code shows. The reviewer read the relevant Blender GPL source
and the removed code. The implementers' accounts of which material they consulted are recorded below.

Questions asked for every piece:

- (a) Structure: functions, order of steps, control flow, loop shapes, data layout. Where the new code has
  the same shape as Blender's, is that shape forced by the mathematics or by our own interface, or is it a
  choice Blender made?
- (b) Expression: names, constants, comments, idioms, error messages. Every constant shared with Blender,
  and whether the description lists it as an interoperability fact with a reason.
- (c) Carry-over from the removed code (which followed Blender).
- (d) The description: code, pseudo-code or recipes that mirror Blender's functions, Blender-internal
  names, rules without a stated basis, and whether the cited references exist and say what is claimed.
- (e) The implementer's provenance statement against the code, the notes and the git reflog of their
  working copy.
- (f) A grade: "no concern", "minor" (cosmetic changes listed precisely) or "substantive" (still mirrors
  Blender: which lines, why, and what an independent formulation would look like in general terms).
- Whether the named tests really judge the behaviour, with a deliberate-break check.

## 3. Piece 1: curve mapping (`src/core/shader_curves.cpp`, implementer A)

### (a) Structure

- Decomposition. Blender has one handle function that computes both handles and applies the Auto Clamped
  limit inside each handle's branch, a table builder that also does the end correction, the overlap
  correction and the sampling (through two helpers in `curve.cc`), one extension function and one lookup.
  The new code splits the work differently: `place_handles` (lines 96-117), `clamp_interior` (120-131),
  `aim_end` (135-143, one helper used for both ends with the handles passed by reference), `de_casteljau`
  (145-152), `build_channel` (154-241), `Channel::extension` (62-78), `Channel::evaluate` (80-92). This
  is an arrangement of its own.
- Sampling. Blender evaluates each segment by forward differencing (repeated addition). The new code
  evaluates each sample directly with de Casteljau's algorithm. Different method, different loop.
- Order of steps. Sort, handles, Auto Clamped limit, end correction, overlap correction per segment,
  sampling, table, extension. Every step needs the previous one's result, so this order is forced by the
  data dependencies, not a Blender choice. The new code computes the extension directions before sampling
  (Blender after); either is correct.
- Table scan (lines 219-239). One forward cursor over the samples, with "cursor == 0 or cursor == m" as
  the outside test and `lower + (upper - lower) * t` for the interpolation. Blender's loop stops its
  pointer at the last sample and weights from the right end with an epsilon test. The new loop is a
  different formulation of the same rule.
- Shared shape not forced by the mathematics: `Channel::extension` (lines 62-78). It has the same
  arrangement as Blender's extension function: test "x <= first", inside it "horizontal -> end value",
  then "direction x == 0 -> end value + direction y * 10000", then the slope formula; the same mirrored
  for the last point with a minus sign in the vertical case; and a final unreachable `return 0`. The
  behaviour (hold, extrapolate, the 10000 rule and its sign) is interoperability and must be reproduced,
  but the branch layout and the unreachable fall-through are Blender's arrangement. It comes into the new
  code through the description (section 6.4 lists the cases in this order, including "Otherwise (cannot
  happen for the callers above) return 0"). The function is 16 lines and contains no other logic.
- `Channel::evaluate` (80-92): "outside the table -> extension from the end entries; index >= 256 -> last
  entry; else linear". Blender's lookup has the same three cases. This is forced: the description's rule
  C9 and any guarded linear table lookup look like this.

`samples_per_segment`, `before_direction`/`after_direction`, `extension`); none is Blender's. Comments refer
to the description's sections and to Farin. Constants shared with Blender:

|---|---|---|
| 2.5614 (Auto handle divisor) | line 43 | yes, C2, [interop], pinned by fixture |
| 10000 (vertical end handle) | line 45 | yes, C10 |
| 1e-6 (end-sample tolerance) | line 44 | yes, C8 |
| 256 intervals, 257 entries | line 41 | yes, C7 |
| 32 samples per segment, s = k/31 | line 42, line 206 | yes, C6 (measured: 33 samples fails) |
| mirror neighbour 2P - P' at the ends | lines 161-162 | yes, C1 |
| float epsilon in the end correction | line 138 | yes, C4 ("epsilon 2^-23") |
| 1/3 for Vector handles | lines 105-106 | basis given (straight segment, Farin), but not marked [interop]; it is also interoperability where a Vector point neighbours an Auto point (the 1/3 then shapes a curved segment) |

| `return 0` in the extension | line 77 | description 6.4, "cannot happen". Blender's fall-through, no basis. |

Not shared: Blender's 1e-20-style guards do not occur here; the coincident-sample test uses an exact zero

### (c) Carry-over from the removed code

The removed code was a compact transcription of Blender's (one loop with an inline end-correction lambda,
forward differencing). The new code does not share its local names (`u`, `v`, `d1`, `d2`, `total`,
`span`, `ratio`, `c1..c3`, `right`), its ternary-heavy clamp, its lambda, or its sampling. Shared items:
the helper types `XY`/`Point`, the parameter names `domain_min`/`domain_max`/`extend` and the whole of
`prepare_shader_curve` were kept in the stub or given by the description's interface section; the error
message "Curve table produced non-finite values" (line 237) is identical to the old line 167. That message
is this project's own text (not Blender's), so it carries no Blender expression.

### (d) The description (`curve-mapping.md`)

- No Blender code and no Blender-internal names (the function names in section 7 are those of Blender's
  Apache-2.0 Cycles exporter, which is correctly labelled).
- It is close to a step-by-step recipe in places: 3.3 (end correction, with the exact assignment
  sequence), 6.2 (the scan with "first point with Q.x > X", "j = 0, or j = m-1 and X >= Q.x", then the
  1e-6 rule), 6.3 and 6.4 (the extension with "multiply first, then divide" and the unreachable "return 0").
  These follow the control flow of Blender's table builder and extension function more closely than a
  behaviour statement needs. Most are marked [interop] and pinned by the fixture, so the behaviour must be
  stated; the order of the branches, the unreachable case, the zero-length guard and the operation order
  need not be.
- Every other rule has a basis: the Blender manual (quotes checked, see below), the fixture, or Farin.
- References checked (21 November 2026): Blender manual, Curve Widget page (5.3): the quotes "mapping
  curves can't have overhang: each X value must correspond to exactly one Y value", "Results in a smooth
  curve without the need to manually set up handles", "Like Auto Handle, but also prevents overshoot",
  "Results in straight lines and a sharp corner", "Causes the curve to 'go flat.'" and "Causes the curve to
  maintain its direction." are on the page. G. Farin, *Curves and Surfaces for CAGD: A Practical Guide*,
  5th ed. (2002) exists; its chapters are 3 "The de Casteljau Algorithm" and 4 "The Bernstein Form of a
  Bezier Curve" (publisher's table of contents, farinhansford.com/books/cagd/toc.html). So "ch. 4" is right
  for the Bernstein form of a cubic Bezier, but de Casteljau's algorithm is chapter 3.

  [Editorial note added when the follow-ups were applied, 21 November 2026: the page cited above is
  the author's own site, and it shows an older chapter layout under the 5th-edition title. The publisher's
  table of contents of the 5th edition (Elsevier, ISBN 978-1-55860-737-8, November 2001; also the O'Reilly
  edition of the same ISBN) and the 5th-edition records of the Texas A&M and Max Planck Digital Library
  catalogues list chapter 3 "Linear Interpolation", chapter 4 "The de Casteljau Algorithm" (section 4.2)
  and chapter 5 "The Bernstein Form of a Bezier Curve". The code and `curve-mapping.md` therefore cite
  ch. 4 (section 4.2) for de Casteljau's algorithm and ch. 5 for the Bernstein form. The rest of this
  review is unchanged.]

Cosmetic changes suggested:

   unreachable `return 0.f` by a stated precondition (the callers only pass x at or outside an end).
2. `place_handles` lines 99-102: remove the "zero length -> 1" guard (unreachable) or replace it by this
   project's own error; it is Blender's guard with no basis of ours.
3. Line 145 (comment of `de_casteljau`): "Farin, ch. 4" -> "Farin, ch. 3"; the header (lines 8-9) can
   cite ch. 3 for de Casteljau and ch. 4 for the Bernstein form.
4. Description: drop the "treat a zero length as 1" sentence (3.1) and the "Otherwise ... return 0" bullet

## 4. Piece 2: hue ramps (`src/core/hue_ramp.cpp`, implementer B)

### (a) Structure

- RGB to HSV. Blender's conversion swaps channels so that the largest comes first, accumulates a sector
  offset `k` and takes an absolute value, with 1e-20 guards against division by zero. The new
  `hexcone_hsv` (lines 39-57) is the textbook form: value = largest channel, chroma, saturation = chroma /
  value with an explicit zero test, hue chosen by which channel is largest (red first on ties, then green).
  Different structure and different arithmetic. The removed code was an unrolled transcription of
  Blender's (four ordered sectors, `std::abs`, 1e-20); none of that remains.
- Arc choice. Blender's hue interpolation function wraps both hues, decides a "mode" in one switch and
  blends in a second switch. The new `choose_arc` (78-101) sets two flags "raise left"/"raise right" from
  the hue difference and applies them; blending happens later in `evaluate`. The comparisons themselves
  (strictness, which side gets the turn, the equal-hue case of Far) are the description's table H3, which
  is behaviour that must match; there is no other way to state them.
- Evaluation (157-178). One `upper_bound` for the right stop (H5, as the stub's old code also did), then
  ordinary convex weights computed from the left end. Blender (and the removed code) weight from the right
  end. Different arrangement; the difference is measured (1.5e-6 against 1.8e-7, both far inside 3e-5).
- `add_interval_boundaries` is this project's own code kept in the stub; unchanged.

### (b) Expression

Constants shared with Blender:

| Constant | In the new code | Listed? |
|---|---|---|
| blue sector offset float32(1 - float32(1/3)) = 0x3F2AAAAA | line 30, with a `static_assert` | yes, H1, with the reason and the two fixture cases that fail otherwise (implementer B confirmed the failure) |
| 1/3 green offset, 0.5 half turn, 6 sectors | lines 29, 83-88, 46 | mathematics of the hexcone and of "half a turn"; strictness is H3 |
| wrap "h >= 1 -> h - 1" once | line 34 | yes, H2 |

Not present: the 1e-20 guards, the swap trick, Blender's names (`k`, `chroma` in that role, `mfac`/`fac`,
`h1`/`h2`, mode numbers).

### (c) Carry-over from the removed code

None beyond the kept interface, the two kept error messages (our own text) and the stub's boundary helper.
`choose_arc` evaluates its Far conditions in the same order as the removed code (equal/negative first,
then positive), but that order is the order of the description's table and has no effect on the result.

### (d) The description (`hue-ramp.md`)

- No code and no Blender-internal names (`hsv_to_rgb` etc. are Cycles' Apache-2.0 functions, labelled).
- Section 5, step 3 gives Blender's weighting arrangement ("f = (x - pR) / (pL - pR) ... products added
  right first"), explained as how the fixture values were produced and declared free. It is optional
  detail; implementer B did not follow it. It could be removed without loss.
- Bases: manual quotes checked and present on the Color Ramp Widget page (5.3): "Blends colors by first
  converting to HSV or HSL, mixing, then combining again", "Clockwise interpolation around the HSV/HSL
  wheel", "Counterclockwise around the HSV/HSL wheel", "Nearest route around the wheel", "Furthest route
  around the wheel". A. R. Smith, "Color Gamut Transform Pairs", SIGGRAPH 1978 (Computer Graphics 12(3)),
  pp. 12-19 exists (researchr.org record) and is the standard source of the hexcone model.

### (e) Provenance statement

Consistent with the code and with implementer B's notes (Linux probe with the real file; break check with 0x3F2AAAAB;

## 5. Piece 3: RGB ramps (`rgb_band` in `src/core/owned_ramp.cpp`, implementer B)

### (a) Structure

- Blender's colour band evaluation is one function for all colour modes: a linear search for the first
  stop after x, three-way handling of "after the last / before the first / inside" with temporary copies
  of stops whose position is overwritten by 0 or 1, then branches per interpolation, with the spline
  weights fetched from the shape-key weight function and applied right to left.
- The new `rgb_band` (lines 32-123): validate the method; `upper_bound`; held ends for the three
  non-spline modes; an explicit interval (left, right) and two outer neighbours set in three cases (before
  the first stop, after the last, inside); the parameter u from the left end; Linear/Ease as
  `left + t (right - left)`; B-Spline and Cardinal as four weights applied left to right, then a
  finiteness check and the clip. The three interval cases and the virtual stops at 0 and 1 are the
  description's interoperability rules R3/R4 and any correct implementation needs them; the rest is its own
  arrangement.
- Weight-vector-then-sum for the splines: the same general shape as Blender's (four weights, one weighted
  sum), but it is also the standard basis-matrix form of every textbook (Foley et al.; Bartels, Beatty and
  Barsky), so it is not a Blender choice. The weights are written differently: Blender's are expanded
  polynomials with decimal constants (for example 0.16666666 and 0.66666666) and the tangent factor folded
  into each coefficient; the new B-spline weights are the textbook (1-u)^3/6, (3u^3 - 6u^2 + 4)/6,
  (-3u^3 + 3u^2 + 3u + 1)/6, u^3/6, and the Cardinal weights are built from the four Hermite basis
  functions and the tangent factor k (lines 104-115).

### (b) Expression

| Constant | Listed? |
|---|---|
| 0.71 Cardinal tangent factor (line 108) | yes, R6 (the reviewer's break check: 0.5 fails 44 comparisons) |
| smoothstep 3u^2 - 2u^3 (line 92) | yes, R5, textbook (Perlin) |
| clip to [0, 1] for the two spline modes only (line 120) | yes, R7 (break check: removing it fails 11 cases) |
| virtual stops at 0 and 1; u = 0 or 1 for a zero-length interval (line 82) | yes, R3 |
| 1/6 of the B-spline basis | textbook |

Names (`after`, `outer_left`, `outer_right`, `right_is_virtual_end`, `w`) are not Blender's.

### (c) Carry-over from the removed code

expression; both match the formula printed in the description, which is the textbook form (not Blender's
expanded one). The error message "RGB spline interpolation exceeded finite precision" is kept on purpose
(own rule in the description). The removed code's interval handling (`reverse` weight from the right,
`before`/`after` neighbours) is not reused.

### (d) The description (`color-ramp-rgb.md`)

- No code, no Blender-internal names, formulas in textbook form with references; every rule marked and

- References: Bartels, Beatty and Barsky, *An Introduction to Splines for Use in Computer Graphics and

## 6. Piece 4: per-object values (`blend_export.py`, implementer C)

### (a) Structure

- `dupli_random_id` (lines 1218-1230). Blender: hash the name; if the persistent id is used, fold each
  entry with the two-word hash, else fold 0; if the root differs, XOR the root name's hash (Blender's one-
  word integer hash is defined as the two-word hash with 0, `BLI_hash_c.hh` line 91). The new code is a
  fold over `list(persistent_id) or [0]` and an XOR with the existing `object_random_id`. The result must
  be bit-identical to Blender's number, so the composition is forced; the expression is its own.
- `_rgba` and `property_rgba` (1238-1281). Blender's C++ switches on the RNA property type and array length
  and reads through RNA calls. The Python version must work on Python values from the API, so it is
  necessarily a different text: type tests, at most five items read, zero-filled RGBA. Lookup order
  (custom property first, even when unusable, then the data path) is the manual's rule ("Custom properties
  have priority over built-in ones").
- `attributes` (1528-1558): particle settings, instance attributes, instancer object, then object and its
  data, zeros. This order is quoted from the manual in the description and is forced.
- Instance attributes. Blender stores, while generating instances, an array of per-level geometry
  pointers and indices, and its lookup loops over that array innermost first. That data is not available
  through Python, so any Python implementation must rebuild the levels from `persistent_id` and the
  geometry API. The new code does this with its own classes: `_InstanceLevel` (1331-1418, instances
  point cloud, component count, a sorted `id` table searched by binary search, cached colour columns),
  `_CollectionLevel` (1421-1434), `_instance_layers` (1560-1583), `_object_level` (1585-1595) and
  `_layer_value` (1598-1605). Nothing here has the shape of Blender's code.

### (b) Expression

Constants: the lookup3 initial value and the string hash belong to the kept, Apache-2.0 Cycles
transcriptions (and lookup3 is public domain); the 0 fold, the XOR, the alpha 1 and the zero fill are O1/O2
with bases; `_INSTANCE_LAYER_LIMIT = 4` comes from the manual ("Currently only up to 4 layers of Geometry
Node instancing are searched", checked on the Attribute Node page) and implementer C's experiment E1; the 2k / 2k + 1
collection numbering comes from C's experiment E4. The type table `_INSTANCE_COLUMNS` follows the
description's table 5.3 row by row; the order of the component names follows section 5.1. No Blender
identifiers occur. The error message for non-finite values is the description's (own rule).

### (c) Carry-over from the removed code

The removed lookup (`_level` returning a 6-tuple, `_instance_attribute` with a list of pending entries,
`_column`, `dict.setdefault` for the `id` map) is not reused; the new code has a different object model and
uses `numpy.unique`/`searchsorted`. Similarities: the local name `kind` in `attributes`; the same sequence
of "if value is None" steps (forced by the order above); a type table with the same keys, properties and
numpy types as the removed one (`_INSTANCE_ATTRIBUTE_TYPES`), in the description's order. The old table was
a mapping of Blender's Python API attribute types, not text from Blender's C++, so its similarity carries
no Blender expression.

### (d) The description (`blender-object-values.md`)

- No Blender code and no internal names (`persistent_id`, `random_id` and the other names are Python API
  names). The rules are stated as behaviour with manual quotes. Section 5.2 is a procedure, but over Python
  API objects, which Blender's code does not use, so it cannot mirror Blender's functions.
- Manual quotes checked on the Attribute Node page (5.3): the Object and Instancer texts, "Custom properties

## 7. Piece 5: switch nodes (`src/core/shader_switches.cpp`, implementer D)

### (a) Structure

- Index Switch. Blender (and the removed code, line for line) builds a chain: a truncation node, then for
  i = 0 ... count one Add node with the offset 1 - i (skipped when the offset is 0) feeding the factor of a
  clamped Mix whose first input is the previous Mix. The new `lower_varying` (lines 357-389) builds a
  balanced binary decision tree over n = trunc(index) with count + 2 leaves (zero, the items, zero), each
  inner node a comparison "n > mid - 1.5" feeding an unclamped Mix. No Add nodes, no clamping, logarithmic
  depth. Entirely different construction. The truncation node is forced by the behaviour (rounding toward
  zero, S4) and by the node set the structural test can evaluate (S6).
- Boolean conversion. `boolean_endpoint` (286-296): vectors through a Vector Math Length node, then a Math
  "greater than 0" node; everything else straight into "greater than 0". Blender's inliner inserts the
  same two nodes for the same conversions. This is the minimal way to express "number > 0" and "vector not
  zero" with Cycles nodes and the only one the structural test's evaluator accepts for numbers (S1, S6);
  it is forced.
- `boolean_constant` (78-98): a chain of type tests; vectors use length > 0 (the removed code tested each
  component against zero) so that constant and graph paths agree. Own arrangement.
- `blend_for` (109-120): a table of Cycles Mix node definitions and socket names (from Apache-2.0 Cycles
  node definitions).

### (b) Expression

No constant is shared with Blender's lowering beyond 0 as the Boolean threshold (S1, manual: "values greater
than 0 are true", checked). The offset 1.5 and the tree are implementer D's. Names are D's own (`lower_varying`,
`subtree`, `leaf`, `at_least`, `nothing`). The error message "Boolean selector requires numeric input" is
this project's own text, required by the description.

### (c) Carry-over from the removed code

None. The removed chain, its `use_clamp`, its offset arithmetic and its `std::visit` conversion are gone.

## 10. Limits of this review

- The reviewer and all implementers are not independent of each other in the way unrelated authors are:
  they share the same background and general training. Code seen before can be reproduced from memory
  without consulting any source during the work; Blender's source is public and widely copied, so such recall
  cannot be ruled out for anyone involved, including the author of the descriptions, who had read Blender's
  source and the removed code. Similar output from parties with a shared background is weaker evidence of
  independence than output from unrelated authors.
- What the implementers looked at is known only from their own statements, their notes and the git reflogs
  of their working copies. A reflog records checkouts and commits, not which files were read or which
  `git show` commands ran. The clone procedure the implementers were given put the old files into the
  working trees of implementers A to C for under a minute; there is no sign they were read, but it cannot be proven.
- Similarity judgments here are informed opinions about structure and wording. They are not legal findings,
  and "no concern" does not mean that a court or the copyright holders would agree.
- The descriptions themselves carry Blender's behaviour in some detail (by design). Where a description
  reads like a recipe (piece 1 most of all), an implementation that follows it will resemble Blender in
  those places whoever writes it; this review cannot separate the description's influence from any other.
- The reviewer read the Blender files at the versions named in section 2 on 21 November 2026, and did not
  compare against other Blender versions. Line numbers refer to those versions.
- One reference (Foley et al., subsection number) could not be verified from a primary source.
- The reviewer ran Linux checks only; no Windows build or render was run for this review.
