## What this project is

- Cycles for Houdini connects the Cycles path tracer (the renderer of the Blender project) to SideFX Houdini.
- The **Render ROP** shelf tool adds a **Cycles Render** output node for Houdini OBJ/SOP scenes. The
  **Cycles Render** Python Panel shows interactive renders.
- It is Windows x64 only. It is built for the Houdini 22.0 build the user has (any 22.0 build with its development
  kit, one build folder per Houdini build). The tested build is 22.0.466 (`certification_candidate` in
  `source.lock.json`, also the official release route's only target); 22.0.429 and 22.0.508 were built and
  quick-tested, and 22.0.508 has also had hands-on use.
- There is no official installer: the project is published as source only. Each person builds for themselves with
  `START HERE - Build Cycles for Houdini.cmd`, whose result is an installer (Setup.exe) per Houdini build. The tool
  never runs a Setup and installs nothing into Houdini itself.
- The Windows build supports CPU rendering without an NVIDIA card and GPU rendering with NVIDIA OptiX. CPU and
  OptiX rendering were tested on the same workstation. See [coverage](../../README.md#what-has-been-tested-and-on-what).
- The integration uses Apache-2.0 and the shipped `blender/` component uses GPL-3.0-or-later. The project has one
  maintainer. Read [README.md](../../README.md) for limits and the open GPU fault.

## Working folders

Everything the commands make stays inside the project folder, in `_work\` (ignored by Git, never part of the
sources): the developer build of the commands below in `_work\dev\windows-h22.0.466-release` (one folder per
Houdini build), test runs in `_work\test-runs`, test tools in `_work\test-tools`, release candidates in
`_work\releases`. The one-file builder uses `_work\windows-h<build>-release`, `_work\cuda-<version>`,
`_work\installer-details`, `_work\kernel-cache` and `Installers\`.

Some folders in `_work` share large read-only inputs with other folders through directory junctions (for example the
`third_party` folder of a second checkout). **Never follow links when removing or copying anything in `_work`:**
PowerShell 5.1's recursive delete and `robocopy` without its option to exclude junctions follow junctions and delete or copy what they point
to. Remove a link as a link first; `scripts/project-layout.ps1` has `Get-ProjectLinks` and `Remove-ProjectLinks`
for this.

## How the pieces fit

Short version (details and file references: [architecture overview](architecture-overview.md), deeper:
[renderer architecture](renderer-architecture.md)):

1. Houdini-side Python reads the scene on Houdini's main thread and hands it to the native module
   `_cycles_houdini` (`src/houdini/`), which converts geometry, materials and lights into owned values.
2. Interactive rendering runs in a separate process, `ch_worker` (`src/worker/main.cpp`), started by
   `houdini/python3.13libs/cycles_houdini/ipr/queued.py`. Scene and image data travel through shared memory.
3. Final renders from the ROP run in Houdini's process by default (`cycles_houdini/core/execution.py`, mode
   `sync`); background renders start a separate `hython` (`cycles_houdini/rop/background_render.py`).
4. The engine is upstream Cycles at `cycles.commit` in `source.lock.json`, plus the files in `patches/` applied in
   the order of `cycles.patches`. Our code never edits `third_party/cycles` directly.
5. The optional Blender bridge starts a separately installed Blender in the background
   (client `cycles_houdini/blender/blend_worker.py`; inside Blender the entry script `blender/worker_main.py` and
   `blender/cycles_blender/worker_server.py`) to read `.blend` files and send meshes and
   material descriptions back to Houdini.

## Build, run, test

All commands run from the repository root in PowerShell 7 on Windows. Prerequisites and versions:
[building from source](building-from-source.md).

```powershell
./scripts/bootstrap.ps1                  # once: fetch upstream Cycles, apply patches/, fetch dependencies
./scripts/build.ps1                      # build and stage; -Jobs <n> for parallel jobs
./scripts/run-hython.ps1 tests/hython_scene_contract.py --device CPU --report $env:TEMP/cycles-cpu.json
./scripts/launch-normal-build.ps1        # open Houdini with this build and its own preferences
python -m pytest -c tests/pytest.ini tests/pytest_cases -m pure
./scripts/run-tests.ps1 -Tier fast -BuildDirectory <build> -Artifacts <folder>
python scripts/format-source.py          # check formatting; --write to apply
```

The full pure suite is tested in a Git checkout. Install Git for the tests that create temporary repositories.
It also needs the pinned test packages (`./scripts/bootstrap-test-deps.ps1 -Download`) and
`houdini/python3.13libs` on `PYTHONPATH`. The test configuration adds `blender/`. Tests that need PySide6
are skipped without it.

### Checking a source ZIP

From the unpacked project folder, use Python and the pinned test packages to check documents and text encoding.
These checks also run without Git. The two Git-backed document test variants skip when Git is unavailable.

```powershell
python scripts/check-doc-paths.py
python scripts/check-doc-paths.py --all-links
python -m pytest -c tests/pytest.ini tests/pytest_cases/test_doc_paths.py tests/pytest_cases/test_text_encoding.py
```

### The one-file builder

People who do not use a terminal double-click one file in the repository root,
`START HERE - Build Cycles for Houdini.cmd` (`scripts/easy-start.ps1`). Its first run checks the computer and
asks separately about NVIDIA downloads and installing missing tools, and lists the installed Houdini 22.0 builds.
With several builds, it asks which to build for (Enter = those without Cycles yet). It then builds and tests
each in its own build folder (`_work\windows-h<build>-release`) and makes its installer (one folder for all:
`Installers\`, one Setup per Houdini build named after it, and a READ ME.txt; details per build in
`_work\installer-details\`). Nothing is created outside the project folder (the CUDA compiler parts go to
`_work\cuda-<version>`; a copy an earlier version put in `%LOCALAPPDATA%\CyclesForHoudiniTools` is copied in, and
earlier `<folder>-build` / `<folder>-installers` folders are named once and left alone). Without Inno Setup 6 it builds
and tests and says that no installer was made. Later runs build (with an installer) for a newly installed Houdini
build by themselves and show a menu (Enter = Close). Unfinished builds remain eligible for retry, and the builder
reports failures before it exits. The builder reads existing Houdini preferences for target selection.
You can run each menu item with `-Action`, or run its script directly:

| Menu item (`scripts/easy-start.ps1 -Action ...`) | Script |
| --- | --- |
| first run (`FirstRun`) | all of the below in order |
| Check this computer again (`CheckComputer`) | `scripts/easy-check-computer.ps1` (may change the NVIDIA download choice, `-CheckOnly` only reports) |
| Update the sources and rebuild (`Update`) | `scripts/easy-get-and-build.ps1`, `scripts/easy-quick-tests.ps1`, then `scripts/easy-make-installer.ps1 -Tested`, for each existing or unfinished build |
| Run the quick tests (`QuickTests`) | `scripts/easy-quick-tests.ps1` |
| Make the installers again (`Installer`) | `scripts/easy-make-installer.ps1` for every built Houdini build (or the one `-Houdini` names) |
| Open Houdini with my build (without installing) (`OpenHoudini`) | `scripts/easy-open-houdini.ps1` (opens a window; never in unattended checks) |
| Turn DLSS off / on (`DlssOff`, `DlssOn`) | sets `dlss` in `build-identity.json` |
| (no menu item) build for another Houdini build (`AddHoudini`) | as the first run, without the computer check; with `-Houdini 22.0.508` also for one that has Cycles installed by a Setup |
| I changed the engine: update the patch files (`EnginePatches`) | `scripts/easy-update-engine-patches.ps1` |

Which Houdini builds: `-Houdini missing` (default: those without Cycles yet), `-Houdini all`, `-Houdini newest` or
`-Houdini 22.0.508` (one build), or the same values in the setting `CYCLES_EASY_HOUDINI`. Each step learns its
Houdini build from `CYCLES_EASY_TARGET_HOUDINI` and `CYCLES_EASY_TARGET_ROOT` (set per build by `easy-start.ps1`);
started on its own, it uses `CYCLES_EASY_HOUDINI` when that names one build, else the newest 22.0 build with the
development kit. Tests redirect the Houdini search (`CYCLES_EASY_HOUDINI_SEARCH`), the Houdini preferences
(`CYCLES_EASY_HOUDINI_PREFS`) and the graphics card (`CYCLES_EASY_NO_NVIDIA=1`); never point the preferences at a
real user's folder in a test.

The steps share `scripts/easy-launch.cmd`, `scripts/easy-common.ps1` and `scripts/easy-houdini.ps1`; `-Yes` or
`CYCLES_EASY_ANSWER=yes|no` answers ordinary prerequisite prompts for unattended runs. Set `CYCLES_EASY_NVIDIA_CONSENT=yes|no`
separately to approve or decline NVIDIA downloads (unattended runs never open Houdini or a
folder window; `-OutputDirectory` puts the installers elsewhere, `-StopBeforeInstaller` makes only the verified
packages), and `scripts/fresh-clone-community-check.ps1` runs the whole path from a fresh clone (`-Zip` from a
downloaded ZIP, `-NoNvidia` as on a computer without an NVIDIA card; test folders go in
`<project>\_work\tests\<name>`, the default, derived from the project folder and never a drive root; keep the
project path short, at most 80 characters, and use short test names such as `_work\tests\t1`). The CUDA compiler
parts come from `scripts/cuda-toolkit-parts.py` (NVIDIA's ZIP archives, never NVIDIA's installer) and are offered
only with an NVIDIA graphics card and explicit approval of the listed NVIDIA parts. Without approval or a usable
CUDA compiler, the build is CPU-only (`scripts/build.ps1 -NoCuda`), and neither
OptiX nor DLSS headers are downloaded. GPU kernels are compiled once and reused by further builds while nothing they
are made from changed: `scripts/build.ps1 -KernelCache <folder>` (builder's path only; the official route never
passes it), `scripts/kernel-cache.py`, stored copies in `<folder>\_work\kernel-cache` (delete the folder to clear
it); `scripts/easy-start.ps1 -NoKernelReuse` or `CYCLES_EASY_NO_KERNEL_REUSE=1` turns it off. What the key covers:
[community builds](community-builds.md), "GPU kernels: compiled once, reused". Nothing in these scripts installs,
updates or downloads a display driver. NVIDIA parts and licences: [NVIDIA licences](nvidia-licences.md). Guide:
[Build it yourself](../user/build-it-yourself.md); reference: [community builds](community-builds.md).

## Which tests for which change

Run the cheapest first; more detail in [tests/TESTING.md](../../tests/TESTING.md) and
[incremental tests](incremental-tests.md).

| You changed | Run at least |
| --- | --- |
| Documentation only | `python -m pytest -c tests/pytest.ini tests/pytest_cases/test_doc_paths.py tests/pytest_cases/test_text_encoding.py` |
| Houdini-side Python | the pure pytest command above, then build and the `fast` tier |
| C++ in `src/` or `include/` | build, the CPU and OptiX scene contract renders (`tests/hython_scene_contract.py`), the `fast` tier |
| An engine patch or `source.lock.json` | `python scripts/engine-fork.py verify`, `python scripts/patch-inventory.py --check`, a full build, the `fast` tier; the `nightly` tier before a release |
| The Blender bridge | the pure tests, then the `nightly` tier with a Blender executable in `CYCLES_HOUDINI_BLENDER` |
| A test file was added, moved or removed | `python scripts/catalogue-tests.py`, then review `tests/test-catalogue.json` |

The `nightly` tier takes several hours and needs an NVIDIA OptiX GPU and Blender; workstation-specific checks need
the maintainer's exact GPUs. Say which tests you ran and which you could not run; never report an untested change as
tested.

## Rules that must not be broken

1. **Tests are never loosened to make them pass.** Do not widen tolerances, skip cases, delete assertions or mark
   failures as expected to get a green result. If a test is wrong, say why, and change it in its own commit with
   the reason.
2. **Engine changes go through the patch series and the lock.** A change to Cycles itself ends as a new numbered
   file in `patches/`, listed in `cycles.patches` with its hash in `cycles.patch_sha256` and the resulting tree in
   `cycles.authoring_tree` (`source.lock.json`), and described in `patches/inventory.json`
   (`python scripts/patch-inventory.py --write`). Existing patch files are not rewritten. Engine edit tool on the
   public engine route: `python scripts/update-engine-patches.py` (double-click: menu item "I changed the engine:
   update the patch files" of `START HERE - Build Cycles for Houdini.cmd`); the maintainer's authoring fork uses
   `scripts/export-engine-patches.py`.
3. **Reference fixtures are not regenerated casually.** Files under `tests/fixtures/` and the committed reference
   images and tables are evidence. Regenerate one only when the reason is understood and stated, with the
   generator named in the docs (for example `scripts/generate-blender-ramp-curve-gate.py`), and say so in the
   commit message.
4. **Licence hygiene.** The shipped Blender component's Python scripts and the six source-only Blender fixture
   generators listed in [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md) carry the `GPL-3.0-or-later` SPDX
   identifier. The Houdini runtime starts the component as a separate Blender process and exchanges data files,
   command-line arguments and pipe messages. `tests/pytest_cases/test_blender_component_boundary.py` checks that
   division and the licence identifiers. Write compatibility code from documented behaviour and standard
   mathematics, with a description and tests in `docs/dev/provenance/`.
   Keep the copyright and licence notices of any adapted Apache-2.0 Cycles code and record the adaptation in
   `THIRD_PARTY_NOTICES.md`. See [CONTRIBUTING.md](../../CONTRIBUTING.md) for the contribution and provenance rules.
5. **Third-party notices stay current.** A new or updated dependency, icon or adapted file needs its entry in
   `THIRD_PARTY_NOTICES.md` and its licence text under `packaging/notices/` (see
   `scripts/fetch-release-notices.py`). Give new source files the applicable `SPDX-License-Identifier` in a comment.
6. **No machine-specific paths or personal data in tracked files**: no user folders, drive letters of one
   computer, e-mail addresses, private scene names or links to private sessions. Use paths relative to the project
   folder and placeholders such as `<project>` or `D:\Example_Folder`.
7. **Keep line endings and encoding.** Some files are CRLF, some LF (`git ls-files --eol <file>`); keep what a file
   has. Text is UTF-8; `tests/pytest_cases/test_text_encoding.py` rejects mis-decoded characters.
8. Do not commit build output, `third_party/`, `.hip` scenes or rendered images (`.gitignore` lists them).

## Making a change

1. Work on a branch (`git switch -c <short-topic>`), never directly on the main branch.
2. Read the code you change and the tests that cover it (`tests/test-catalogue.json` names them).
3. Make the smallest change that does the job. Add or extend a test that fails without it.
4. Build and run the tests from the table above. Do a test render on CPU (and OptiX if you have it).
5. Format: `python scripts/format-source.py --write` (needs clang-format 18.1.8 and Ruff 0.14.3; pass
   `--clang-format <exe>` and `--ruff <exe>` if they are not on `PATH`), then run it again without `--write`.
6. Commit with a message that says what changed, why, and which tests ran. See
   [CONTRIBUTING.md](../../CONTRIBUTING.md) for pull requests.

## Pitfalls

Each one is checked in the code.

- `import cycles_houdini` does not load the native DLL; the first native call does. Pure tests therefore run with
  ordinary Python and no Houdini (`houdini/python3.13libs/cycles_houdini/README.md`).
- Houdini (HOM) calls belong on Houdini's main thread. The interactive controller (`ipr/queued.py`) must not call
  HOM; Qt widgets belong to the GUI thread.
- Scripts that run inside Blender start with `--factory-startup` and inherit no `PYTHONPATH`
  (`blender/worker_main.py`); they cannot import Houdini modules.
- `scripts/bootstrap.ps1` never replaces an existing `third_party/cycles`, only checks it. After a failed download
  delete `third_party/cycles.incomplete` and run it again.
- Run `scripts/catalogue-tests.py` on Windows. It writes the platform's line endings (`tests/test-catalogue.json` is
  CRLF) and sorts paths the platform's way (case-insensitive on Windows), so on Linux `--check` reports "stale" and
  a regenerated file reorders entries even when nothing changed.
- The official release route (`scripts/build-release.ps1`, `scripts/release-source.py`, and
  `scripts/release-package.py` without `--build-identity`) refuses a build made from the public engine route; see
  [building from source](building-from-source.md). Public clones make installers with
  `START HERE - Build Cycles for Houdini.cmd` (`scripts/easy-make-installer.ps1`): a community build with its own
  identity from `build-identity.json` (own Windows app id, install folder and Houdini package file; never the
  official ones). Do not change the official identity in `release-package.py target_identity()` or the defaults in
  `packaging/installer/CyclesHoudini.iss`; `tests/community_build_test.py` pins them.
- DLSS: the official NVIDIA project identifier is in `patches/0077-houdini-dlss-project.patch`. Community builds
  use their own (`dlss_project_id` in `build-identity.json`, generated on first use), compiled through the
  top-level `CMakeLists.txt` setting `CH_DLSS_PROJECT_ID` (`scripts/build.ps1 -DlssProjectId`), which compiles a
  copy of `third_party/cycles/src/integrator/denoiser_dlss.cpp` with only that identifier replaced; empty (the
  official route), nothing changes. `"dlss": "off"` (or `-Dlss:$false`) builds without DLSS; community builds are
  DLSS on by default (decided 21 November 2026), fetch the DLSS headers only with an NVIDIA graphics card
  (`scripts/bootstrap.ps1 -SkipDlss` otherwise), and never contact NVIDIA.

## Formatting

The production C++ style uses clang-format 18.1.8 and a 120-column limit. Python uses Ruff 0.14.3. Run
`python scripts/format-source.py` before committing. Use `--write` to apply changes. Supply `--ruff <executable>` and
`--clang-format <executable>` when the tools are outside PATH. The check covers tracked integration, harness,
Python, script and test sources. Vendored headers and frozen fixture files retain their original bytes.

## Keeping these documents accurate

`python scripts/check-doc-paths.py` checks that every path, script and script option named in the entry documents
(README, CONTRIBUTING, this guide, the architecture overview and the build guide) exists; with `--all-links` it also
checks every relative link and heading anchor in every Markdown file. Both run as the pure test
`tests/pytest_cases/test_doc_paths.py`.
