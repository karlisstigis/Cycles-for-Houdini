# Qualify Houdini builds by major/minor version, HDK ABI and dependencies

Accepted 2026-11-10. The production baseline is Houdini 22.0.466. The following is the target load policy for the Phase 1 implementation.

| Host at load time | Result |
| --- | --- |
| Exact build with matching HDK ABI and required DLLs | Load normally. |
| Different build within the same major/minor, with compatible HDK ABI and required DLLs | Load with one warning per session in status and log. Include the package build and running host build. |
| Different major/minor, incompatible HDK ABI, or missing or incompatible required DLL | Fail with the specific mismatch. |

Use the recorded HDK API version to check the ABI. Studios can opt into exact-build matching with `CYCLES_HOUDINI_STRICT_BUILD=1`. A successful compatibility check establishes eligibility to load. The release page lists the exact builds exercised.

Houdini discovers native DSOs before Python startup. At staging or registration, package eligibility enumerates installed builds and names only exact versions whose SDK header reports the built HDK API and whose required SDK OIDN DLL identities match. A compatible alternate is included only when already installed; its package expression also excludes it when `CYCLES_HOUDINI_STRICT_BUILD=1`. Installing another Houdini build later requires refreshing registration. The Python runtime check repeats the major/minor, HDK API and DLL checks and produces the one-time warning for an eligible alternate. An incompatible build is filtered before Python loads, so it cannot show that in-session warning; it has no Cycles operator or DSO. Packages with overlapping eligible build sets cannot share a preference directory.

After installing another Houdini build, run `Refresh Cycles registration.cmd` in the Cycles application folder and leave the optional path blank to scan standard Program Files installations. For a Houdini build installed elsewhere, enter its full folder path at the prompt or run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File '<Cycles application folder>/tools/refresh-registration.ps1' -HoudiniRoot '<Houdini folder>'`. The refresh remembers custom Houdini roots in this installation's state. Entering a second custom path or leaving the prompt blank retains the first while it remains compatible; a removed or changed custom SDK is reported and removed from eligibility. This uses the installed package's frozen HDK API and OIDN DLL record, checks for another eligible Cycles package in the same preferences, and updates only the current package's owned eligibility expression through the existing transaction journal. It does not switch the active payload or touch other registrations. A newly entered incompatible build prints the specific version, HDK API or DLL mismatch while preserving the current registration. The launcher is installed alongside the application even when Setup uses a nondefault `/DIR` path. A host excluded before DSO discovery cannot display an in-session warning; run this refresh action to get the reason.

To distinguish an HDK ABI break without loading the plugin, compare `HDK_API_VERSION` in each installation's `toolkit/include/UT/UT_HDKVersion.h`. For example, `Select-String -Path 'C:/Program Files/Side Effects Software/Houdini 22.0.429/toolkit/include/UT/UT_HDKVersion.h','C:/Program Files/Side Effects Software/Houdini 22.0.466/toolkit/include/UT/UT_HDKVersion.h' -Pattern '^#define HDK_API_VERSION'` reports `22000425` and `22000453` respectively. Different values require separate native builds.

Provide an on-demand workstation CI job that rebuilds against each selected Houdini SDK and uses that build’s own dependencies. The first candidate matrix is 22.0.429 and 22.0.466. For each entry, verify native module loading, the worker handshake, a CPU image, an OptiX image and clean process exit. Record the build and results before listing it as qualified. Running this job is independent of packaging, activation and the full nightly.

Implementation: enqueue the opt-in job with `python scripts/workstation-ci.py enqueue compatibility <revision> --houdini 22.0.429 --houdini 22.0.466`, then run the configured drain. Each selected SDK gets its own build directory, manifest and receipt. The focused qualification also renders Image Iris on CPU. A passing receipt records an exercised exact Houdini build and integration revision; it is unsigned and does not activate or package the build. The normal fast and nightly jobs remain separate.
